# PinK 独立自动化框架第一版方案

日期：2026-10-17。状态：方案草案，未实现。已确认独立 PinK-Test 的方向；执行器、接口格式及实施批次仍需确认。本方案遵循[需求基线](pink-automation-requirements-baseline.md)，不增加业务用例或平台范围。

## 目标和首批样本

PinK-Test 独立维护用例、材料、链路、运行入口和结果，不要求测试组准备完整 PinK 源码及开发环境。目标是让链路既能单独执行，也能在同一测试集合中串行执行，并允许后续持续增加用例。

首批设计用两个不同样本检验框架：现有 Windows 构建工具，以及 E01「基础编辑与保存重开」。E01 是设计样本，不代表已批准自动化实施或材料已经可用。构建当前终点仍为构建成功，不扩展到产物运行、原生编译或上传。

建议首次验证使用与现有构建工具相同的 Windows 目标包及已准备环境，减少同时引入新环境的变量；具体包和材料在实施前确认，不据此承诺跨版本或 macOS 兼容。

## 架构和职责

```text
用例与材料约定 → 测试集合 → 本轮执行计划
                                  ↓
                         独立命令入口与运行器
                            ├─ 构建适配 → 既有构建工具
                            └─ 编辑链路 → 局部 UI 驱动
                                  ↓
                        统一汇总与链路原始证据
                                  ↓
                         QA 查看或后续 AI 分析
```

| 部分 | 职责 | 不承担的内容 |
| --- | --- | --- |
| 用例及执行数据 | 引用业务用例编号和修订，绑定材料、输入、预期及必要检查点 | 不把 UI 选择器放进业务预期 |
| 测试集合 | 选择链路及用例实例，明确平台、配置和适用条件 | 不复制用例实现，不穷举全部组合 |
| 公共入口与运行器 | 展开计划、串行调用、管理运行状态和报告位置 | 不理解构建字段、Sprite 或场景编辑业务 |
| 链路及适配 | 组织业务步骤、等待、断言，关联原始结果，报告能否安全继续 | 不负责调度其他链路 |
| 局部 UI 驱动 | 定位具体面板和对象，执行真实点击、输入、拖拽和状态读取 | 不决定业务预期，不直接宣称用例通过 |
| 材料与结果 | 记录初态和恢复点，保留原始材料、工作副本与可追溯证据 | 不通过重置或脚本自修复掩盖产品错误 |

用例与链路不强制一对一。一条链路可覆盖多个相关用例，同一用例可以有多个平台或配置实例；点击数、步骤数和平台数不能直接作为通过用例数。

## 推荐的执行路线

优先以成熟测试运行器承担筛选、测试生命周期、断言和报告扩展，独立入口只负责传入本轮目标和测试集合，不自研另一套通用调度引擎。Playwright Test 作为首选验证候选，不在本次冻结具体版本。

候选依据是其已有[环境准备与清理机制](https://playwright.dev/docs/test-fixtures)和[报告扩展](https://playwright.dev/docs/test-reporters)。这些机制不能自动隔离外部 PinK、工程和构建任务，仍需链路报告真实环境状态。

首次设计采用单 worker、关闭自动重试；不使用“某条失败就跳过全组”的依赖式串行来代替独立链路。运行器与连接方式分开选择：UI 优先使用外部 Playwright/CDP，构建继续沿用现有连接方式，不自动改成内部 Automation Bridge。

PinK 内部基座只作为可选复用候选。Driver、稳定定位和连接恢复的设计可以参考；代码复用需先确认独立交付、版本和依赖边界，不整套复制后两边维护，不为接入框架新增产品接口。正式测试需要的内部查询如果没有独立可用方式，记录缺口再决定是否局部复用，而不是假定必须绕开所有内部能力。

## 哪些复用和哪些新做

| 内容 | 第一版处理 |
| --- | --- |
| 现有构建工具、配置、等待、任务观察和截图 | 直接复用正常命令入口；不重写业务流程 |
| 已有构建结果 | 保留原 schema、原文件和原结论，通过适配读取；不批量迁移历史报告 |
| 已有构建连接代码 | 构建链路继续使用；编辑链路只按需要复用可独立使用的部分，不先抽通用启动平台 |
| 已确认用例和材料设计 | 引用当前唯一维护位置，只补选定样本的可执行绑定 |
| PinK 源码自动化基座 | 参考现有能力；不设为框架运行前提，不整套搬迁 |
| 公共入口、计划和汇总 | 需要新做，使用成熟运行器的扩展点，保持轻量 |
| 构建结果适配 | 需要新做，负责本轮结果关联、实例和检查点映射 |
| E01 自动化和局部编辑驱动 | 需要新做并验证，优先外部 UI 操作，不直接搬用内部冒烟测试 |
| 环境安全衔接 | 需要补齐目标身份、活动任务、连接有效性及能否继续的确认 |
| 前端、AI、版本触发和证据上传 | 后续接入，本批只准备可读取的结果，不实现服务或平台 |

建议新增实现位置为 `tools/framework` 和 `tools/editor-ui`，既有 `tools/build-ui` 保留。首版不把每个职责拆成发布包，不建设插件注册、动态发现或万能步骤语言；实际文件拆分在实施时确定。

当前构建工具另有独立历史页面检查入口，其已有改动保持不变，不因框架设计默认纳入首批或重构。

既有行为以[构建工具说明](../tools/build-ui/README.md)和[当前构建入口](../tools/build-ui/src/cli.ts)为依据，新框架接入后的行为另行验证。

## 构建链路如何接入

第一步以现有 web-desktop 单平台命令作为接入样本。由构建工具自己启动或连接目标 PinK，并负责配置、提交、观察和收尾；外层不同时控制同一实例。现有多平台批次内部的每组两项和任务队列规则保留，外层不再拆分其业务调度。

适配负责以下工作：

1. 为本次调用分配独立的结果根目录，记录请求参数及预期实例；通过直接进程参数调用既有命令，不拼接 shell 字符串。
2. 收集退出码和日志，并核对报告的本轮身份、目标包、工程、平台、配置、任务归属和终态；没有报告、报告截断或参数错误都不能当作通过。
3. 把有证据的检查点关联到对应业务用例及实例，保留原始任务和截图引用。不能因为工具名或平台相同，就把它记为 B01–B09 完整通过。
4. 报告产品任务是否收尾、观察是否可靠及是否可以继续。仅子进程结束、调试连接关闭或退出码为 0，都不足以证明环境已可复用。

当前构建结果围绕平台和 profile，尚不是完整的业务用例记录。无法准确映射的结果保留为工具检查证据，不虚构用例编号或增加通过数。schema 3/4 的处理限于已声明支持的格式；未知格式明确报错，不猜字段。

第一次接入不改构建执行逻辑。若确认“能否继续”所需状态无法通过现有报告或只读预检获得，再提出最小必要的工具输出调整。现有工具保留单独运行能力。

## E01 编辑链路如何设计

完整操作和预期仍以[用例清单 E01](pink-regression-cases.md#e01-基础编辑与保存重开)为准，本节只说明自动化接入点。

| 环节 | 链路职责 | 必须留下的判断依据 |
| --- | --- | --- |
| 准备 | 使用材料设计中的编辑材料和干净初态，在工作副本中运行 | 工程、场景、父节点、图片与 SpriteFrame 身份及初值 |
| 编辑 | 真实 UI 新建节点、调整关系、添加 Sprite、设置引用和位置、重命名 | 操作对象明确，层级、Inspector 和可见图片符合目标 |
| 保存与场景重开 | 经被测入口保存，关闭场景后重开 | 保存目标的名称、关系、组件、属性、引用及图片仍正确 |
| 工程重开 | 关闭并重新打开同一工程，重新定位窗口和面板 | 再次核对同一保存结果；不能把整个应用重启视为自动等价 |
| 收尾 | 保存结果或失败现场，说明剩余连接、弹窗、dirty 状态和工作副本位置 | 必要检查点是否完成，以及是否可以继续其他链路 |

初始材料可以预置，但不能通过脚本或接口提前完成 E01 正在验证的创建、编辑和保存，也不能在重开时自动补回节点。两次重开分别记录，任一必要检查点未完成就不能判 E01 通过。

优先读取真实 UI 及可靠的持久化结果，与事先定义的预期核对，不根据实际结果反推预期。截图用于辅助核对图片和定位故障，不能单独证明组件引用或保存正确；独立方式无法可靠观察时先保留阻塞，再评估局部状态查询。不能把“按钮点击成功”降低为通过标准。

尚需在目标安装包确认：工程完整路径和场景身份如何读取、新建及组件操作入口、两种重开的连接变化、引用与持久化结果的观察方式，以及自动保存和弹窗等前提。材料文件存在不代表这些能力已验证。

## 最小输入输出和执行安全

| 对象 | 必需信息 |
| --- | --- |
| 本轮输入 | 目标 PinK 路径和预期身份、测试集合、材料位置、输出位置及必要阶段预算 |
| 执行实例 | 用例编号与修订、链路、平台或配置参数、材料身份、必要检查点及适用条件 |
| 实例结果 | 实际目标身份、通过或失败等业务状态、已完成和未完成检查点、预期与实际、原因和证据位置 |
| 链路收尾 | 活动任务或未保存状态、观察是否可靠、环境可继续／不可继续／未知，以及原因 |

本轮先保存计划，再执行。汇总对照计划逐项核算，区分通过、失败、阻塞、跳过、未执行和中断；运行器本身的状态单独保留，不把材料阻塞全部混成产品缺陷。原始报告保存在链路目录，公共汇总引用它，不改写旧文件。

不依赖工作进程内的一个布尔值证明环境安全。Playwright Test 在失败后可能[重建 worker](https://playwright.dev/docs/test-retries)，下一条链路仍须重新确认产品状态；上次未正常收尾或证据缺失时按未知处理，不能自动继续写操作。

等待和只读查询可以在预算内重试，点击、创建、提交构建等写操作不自动重复。公共超时不能先截断链路正常的排队、处理及诊断预算；异常终止时标记结果不完整，不根据遗留半份报告判通过。不强制关闭用户 PinK、不取消用户任务、不清全局数据，也不要求首版支持暂停续跑。

构建与编辑可使用不同工作副本或不同会话，不要求共享一个窗口。涉及关闭、重开和恢复的操作只能作用于明确归属本轮的测试上下文。已有构建工具对当前会话的要求先保留，尚不能切换到正确工程时阻塞，不通过误连同名窗口继续执行。CDP 的[能力限制](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp)也意味着不能预先承诺所有跟踪或高级交互可直接使用。

## 后续怎样增加用例和链路

| 变化 | 应修改的地方 | 不应修改的地方 |
| --- | --- | --- |
| 已支持行为增加一组输入或平台实例 | 对应执行数据和测试集合，补明确预期 | 公共运行器、其他链路 |
| 已有链路增加新的业务检查 | 用例约定、该链路断言及必要证据读取 | 不把业务判断塞进公共报告层 |
| 新平台带来新控件或参数语义 | 平台事实、局部驱动及预期映射 | 不承诺只加平台名称即可覆盖新行为 |
| 新增业务链路 | 自己的操作与核验实现，接入共同输入、结果和收尾约定 | 既有构建或编辑流程 |
| PinK 升级导致 UI 改变 | 对应版本的局部驱动，按实际影响验证 | 不改业务预期以迎合错误行为 |

人读用例继续作为业务合同；选定用例的机器执行数据只是其可执行绑定，关联同一编号、修订和检查点。具体目标值只在对应执行数据中维护，Driver 不再抄一份预期；合同改变时校核绑定，不另建一套独立业务清单。首批不解析或迁移全部 38＋24 条，也不设计任意自然语言步骤执行器。

新增链路可通过静态显式登记接入，无需动态插件系统。普通实例变化不改公共运行器，新业务行为允许增加局部代码；这才是本方案的可扩展边界，而不是所有用例都零代码。

## 建议实施顺序及验收

| 阶段 | 在范围确认后做什么 | 推进条件 |
| --- | --- | --- |
| 接入前核实 | 确认目标包、E01 材料和可靠操作／核验入口，验证成熟运行器能承接既有命令 | 不需要完整 PinK 开发环境；若需要内部能力，先说明最小依赖和代价 |
| 最小实现 | 公共入口、计划和汇总，接入一个既有构建实例及完整 E01 | 两条链路各自可运行，业务判断不依赖另一条结果 |
| 组合与异常核验 | 串行组合，检查报告缺失、未执行及环境未知时停止后续操作等关键行为 | 所有计划实例都有交代；不得重提未知构建或误操作用户实例 |
| 扩展验证 | 在已支持行为内增加实例，确认不需改公共执行器 | 扩展的是已批准范围，不借架构验收增加平台或业务用例 |

可复用现有有效构建证据，但框架接入、E01 和环境衔接仍需自己的实际证据。产品缺陷导致某个业务用例失败可以如实交付失败报告，不伪造全绿；E01 的操作能力未完成或结果不可判定，则不能称为链路已完成。

进入代码实施前还需确认：目标环境与包、E01 是否为正式首批、材料和关键观察值、执行器及兼容依赖版本、阻塞对整轮结论的处理。本方案不授权改 PinK／CLI／插件、执行整套回归或扩充构建验收终点。

前端与 AI 后续消费同一份汇总及原始证据。AI 的只读诊断不覆盖机器结论，补测写操作另按授权执行；首版不实现模型服务、自动上传、禅道同步或版本发布调度。
