# PinK 自动化测试需求基线

冻结日期：2026-10-17。冻结对象是需求目标、职责和范围，不是技术选型、接口细节或具体开发批次；本次不启动代码实施。

## 核心目标

建立可扩展的 PinK 自动化测试框架，让测试组能够重复执行已确认的回归用例，也让主机能够在版本更新后按指定测试集合自动执行、收集证据并汇总结果。

业务用例定义要保护的行为，测试链路负责真实操作与核验，公共框架负责组织执行和结果汇总。各条链路可以独立运行，也可以组合运行；后续新增用例和链路不需要重写整个工具。首批通过基本用例和构建链路落地这一能力。

这是一项新增的公共框架需求，不再只是微调 Creator 测试工程或完善构建脚本；但也不等于建设测试管理平台。

业务方向保留测试组提出的四类：编辑器稳定功能回归、PinK 新增功能的回归、PinK Agent 对话功能，以及构建面板 UI 与构建结果。首批先落地基本用例和构建链路，其他方向不因框架冻结就默认进入首批；新增功能也先判断哪些行为值得长期回归，不要求每个新功能立即全部自动化。

## 首批交付范围

| 部分 | 首批要求 | 边界 |
| --- | --- | --- |
| 公共执行框架 | 提供不依赖前端的本地执行入口，选择测试集合，调用链路并汇总结果；同一桌面上的 UI 链路先串行运行 | 不要求云端调度、多机并发或完整流水线平台 |
| 基本回归链路 | 从已确认的用例中选择有代表性、材料和预期明确的一批，形成实际可运行链路 | 具体用例编号和数量在实施批次中确认，不默认全量自动化 |
| 构建链路 | 延续现有工具及证据，支持构建面板真实 UI 操作、配置核对和实际构建结果核验，并能独立执行 | 不把当前“构建成功”升级为已经验证产物、运行或全部构建用例 |
| 测试项目和材料 | 为选定用例提供明确初态、资源、输入和恢复方法；与执行工具分开维护 | 不复制整个历史项目，不默认依赖旧 L10N；涉及 L10N 时使用对应 PinK 随包插件 |
| 结果和证据 | 输出结构化结果、执行目标、预期与实际、失败原因及日志和截图等证据位置 | QA 和 AI 可读取；不依赖 AI 才能执行或判定固定检查点 |

当前业务用例仍由[首轮回归用例](pink-regression-cases.md)维护，材料由[测试项目与材料设计](pink-test-project-design.md)维护。本基线不另建一套用例清单。已有 38 条首轮及 24 条条件补测不是首批全部自动化的承诺。

## 构建业务的覆盖目标

按 QA 已明确的方向，构建页面需要完整的用例设计，覆盖页面 UI 行为和构建管线正确性。完整设计、分批实现和执行矩阵是三个不同问题：

- 完整设计要说明有哪些行为、正常与异常分支，以及如何判定正确，不能只验证按钮可点击。
- 实现按已批准的批次推进；既有 Windows 工具的当前终点仍为构建成功。
- 平台、配置和环境组成执行实例，不默认把所有排列组合都跑一遍。平台专属行为和必要组合由用例选择依据决定。

产物核验、启动运行、原生编译、上传等阶段是否进入某一批次，以及各平台的验收终点，需要分别确认。公共框架接入不自动扩大这些边界，也不把当前冒烟结果等同于构建页面完整覆盖。

## 分工与扩展要求

| 对象 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 用例 | 稳定编号、业务目标、前提、材料、操作、检查点、预期和适用条件 | 不绑定公共运行器的内部实现 |
| 测试材料 | 工程、场景、资源、配置、故障输入和可恢复的初态 | 不承担 UI 驱动或结果汇总 |
| 测试链路 | 具体产品操作、等待、断言、证据收集及必要的准备和收尾 | 不接管其他业务链路 |
| 测试集合 | 选择本轮用例及平台、配置等执行实例 | 不复制维护业务预期 |
| 公共框架 | 接收目标和测试集合，组织执行，记录状态并汇总报告 | 不理解构建字段、场景组件或 Agent 业务细节 |
| 使用界面与 AI | 展示用例和真实结果、辅助启动和分析 | 不成为执行前提，不覆盖原始自动化结论 |

用例与链路不是强制一对一：一条链路可验证多个相关用例，一个用例也可产生多个平台或配置实例。

扩展需满足三个要求：

1. 已支持行为下增加普通用例或实例，主要调整数据和预期，不修改公共运行器。
2. 新增链路有自己的执行实现，接入共同的输入和结果约定，不要求改写既有链路。
3. 新控件、新平台特性或新操作可以增加局部适配代码，不承诺所有新用例都能零代码配置；不为此预先建设万能步骤语言或动态插件系统。

具体框架、语言、目录结构和接口格式留到下一阶段设计，先用真实的基本链路与构建链路验证哪些能力值得共用。

## 自动执行与结果可信性

自动化默认执行设计好的流程和明确断言，不要求 AI 每一步看图决定操作。测试 UI 的行为必须经过真实 UI；准备无关前提或读取实际结果可以复用已有接口，但不能绕开目标操作后声称 UI 已通过。

每轮应记录测试集合及版本、目标 PinK 和实际可确认的运行身份、材料身份、用例实例参数、预期与实际及证据位置。目录名称或命令退出成功不能单独证明版本正确或用例通过。

本轮计划的执行实例都要有交代，区分通过、失败、阻塞、跳过和未执行；缺失报告或未知状态不能算通过。点击数不等于通过用例数。重试保留原失败和各次记录，人工复核及 AI 分析与原始机器结论分开保存。

链路超时或断开后，需要区分产品操作是否仍在进行、环境是否可以继续使用。不能只因执行进程退出就启动下一条 UI 链路，也不能默认强制关闭 PinK、取消用户构建或重置用户配置。停止能力可按链路明确支持范围，不要求首版实现暂停续跑。

无人值守 UI 测试仍需可用的桌面会话及必要 SDK、权限、登录和测试材料。运行中需要人工处理时应明确等待或阻塞，不能把这类链路描述为已具备无人值守能力。

## 后续能力与明确不做事项

长期方向是让版本流程调用同一执行入口，运行当版维护的测试集合，并让 QA 和 AI 读取结果。首批由调用方提供目标安装包或可用实例及测试集合，不要求框架自动发现、下载、安装或分发版本。

| 后续按需要接入 | 不作为首批前提 |
| --- | --- |
| 新链路、新用例及条件补测 | 全量 Creator 历史用例迁移、全平台与全部配置穷举 |
| 测试组的用例展示、启动入口和进度结果界面 | 账号权限、多人协作、云端调度和机器管理平台 |
| 外部版本触发或 CI 调用 | 自建版本发布系统、下载器、通知系统或趋势看板 |
| AI 读取报告辅助分析 | AI 自动修改预期、自动修复链路或自动提交缺陷 |

禅道继续负责缺陷提交、处理和闭环，不另建 Bug 系统。把工具做成 PinK 插件、让 PinK Agent 充当执行器，以及产品核心、CLI、SDK 改造，都不是公共框架的默认前提；确有必要时单独说明依赖和范围。测试 Agent 产品行为与依赖 Agent 执行整个测试是两回事。

## 下一阶段需要确认的事项

- 首批基本用例的具体编号、材料可用性及对应链路。
- 首批操作系统、目标安装包和可自动执行的环境前提。
- 构建完整用例设计与当前实现的差距，以及下一批平台、配置和验收终点。
- “每版本全用例”的测试集合定义、条件补测触发规则，以及阻塞或未执行对整轮结论的影响。
- 公共入口和链路的最小输入输出约定，以及现有构建工具如何接入；技术选型随后决定。

首批框架验收应通过真实的基本链路与构建链路证明：可以分别运行、组合运行并生成完整可追溯的汇总；链路互不混淆结果；在已有操作能力内增加用例不必修改公共运行器。已知环境限制、失败和未执行必须如实呈现，不以全部变绿代替框架验收。

后续新增业务范围、验收阶段、平台矩阵或产品侵入点需明确确认。本次冻结不触发整套重测，也不改变已有工具的开发授权；实现前再确定具体批次。
